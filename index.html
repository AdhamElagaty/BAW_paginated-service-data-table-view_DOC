Paginated Service Data Table View

A server-driven data table for IBM Business Automation Workflow. It requests exactly one page of records at a time from an AJAX data service, and lets that same service turn any column into a button, badge, progress bar, toggle switch, link, or custom HTML fragment — with zero extra Coach View design work.

Server-side pagination Offset & cursor modes Dynamic column engine Auto-discovery mode
01 — Overview

What this view is

The Paginated Service Data Table View renders tabular data the same way a standard Table view does — rows built from Text, Decimal, Display Text and similar controls — but it never holds more than one page of records in the browser. Every navigation action (Next, Previous, First, Last, page-size change, refresh) calls a bound Pagination data service, which is responsible for returning just that page.

The service response can also carry a list of columnConfigurations — small JSON payloads, one per column — which the view interprets at render time to swap a plain text cell for a live component: a colored status badge, a toggle switch, an inline progress bar, an action button, a hyperlink, or a raw HTML fragment with click hooks. Because that configuration travels with the data, a backend developer can change how a column looks and behaves without ever reopening the Coach View designer.

Mental model: A standard Table view is a window over an array that already lives in memory. This view is a window over an array that lives on the server — the browser only ever sees the slice it currently needs.

02 — Benefits & Comparison

Why use it instead of the standard Table view

The standard Table and Service Data Table views are excellent for small, already-loaded lists. This view exists for the cases where that assumption breaks down: large record sets, expensive queries, and columns whose appearance needs to be decided by business logic rather than fixed at design time.

Scales past memory

Only the current page is ever transferred or held client-side, so record counts don't bound what the view can display.

Columns are data, not design

Badges, buttons, toggles and progress bars are described in the service response, not hand-wired per view instance.

Two pagination strategies

Works with classic offset/page-size backends and with cursor/token-based APIs, including ones that can't report a total count.

Data binding & architecture differences

Uses "Async loading" and "Async batch size" properties to prevent UI lockups, but browser memory is ultimately limited by the total payload size. True server-side pagination. Only fetches and stores exactly pageSize records per request via the bound Pagination data service. Scales infinitely regardless of backend database size.
Data Source Binding & Structure Bound list strictly dictates the layout. Developers must drag-and-drop individual inner controls (Text, Decimal, Coach View) for each column into the table drop-zone on the Coach canvas. The wrapper still binds to a list (for framework compatibility), but rows are generated dynamically. columnConfigurations JSON payload dictates column structure. No manual drag-and-drop column design required.
Rich Cell Rendering Requires setting Render as: Custom and writing explicit DOM manipulation JavaScript (e.g., document.createElement("div")) in the On custom cell event, or setting Render as: Seamless Coach View which can impact performance. Fully declarative via JSON componentType (Badge, Switch, Button, Progress, Icon, Link). The view executes DOM creation internally. Requires zero Coach View DOM scripting.
Adding & Deleting Rows Built-in configuration toggles for Show Add button and Show Delete button. Native operations modify the local client-side array and trigger On row added / On row deleted events. No built-in UI buttons for Add/Delete operations. Relies on a server-driven architecture using Custom Cell Buttons (e.g., actionName: "DELETE") triggering On custom cell action to update the DB and call view.refresh().
Sorting & Filtering Client-side. Users click column headers to sort the local memory, or developers call the search(), clearSearch(), and getFilteredRecords() APIs. Clicking a sortable header performs a client-side sort only on the currently visible page of records. It also triggers the On sorting by column header event, which allows you to pass the col and order to your backend query for true server-side sorting.

03 — Requirements & Setup

What you need, and how to wire it up

There is exactly one hard requirement: an AJAX service that understands the four input variables and returns the three output variables described in the Data Service I/O section. Everything else is optional configuration.

Before you start

  • An AJAX service created from Default Table Paginated Data Service that can page through your data source by index or cursor.
  • A clear answer to "can I calculate a total row count cheaply?" — if not, plan to return totalCount = "-1" and rely on Next/Previous-only navigation.
  • A decision on whether columns should be entirely auto-discovered from the data, or explicitly authored server-side with columnConfigurations.

Setup steps

  1. Drop the view onto your Coach and bind the data service

    Provide a standard Business Data list binding to the view (variable of type ANY List), then set dataService to your AJAX service (or default). Optionally bind input to a filter object your service reads to scope the query.

  2. Implement the service contract

    Read pageIndex, pageSize and/or cursor, query your data source, and return result, totalCount and, if using cursor pagination, newCursor.

  3. Choose strict or auto-discovery columns

    Leave Only show configured columns off to let the view build columns from the first record's properties, or turn it on and describe every column explicitly via columnConfigurations.

  4. Set the chrome

    Toggle Show "Items per page" dropdown, Show refresh button, Show next/previous buttons, Show first/last buttons and Show page indicator to match the navigation you want visible, and set the pageSize list.

  5. Wire the events you need

    Handle On custom cell action for any interactive cell, On result/On error for post-fetch logic, and On row selected by user if selection drives other views.

  6. Prototype the JSON before you wire BAW

    Use the companion Simulation Lap IDE Studio to design your data shape and column configurations visually, then export the generated service script straight into your data service.

05 — API

Events

All events are exposed through the standard Coach View event-binding mechanism and can be wired to boundary events, inline JavaScript, or downstream services.

On loadEvent

Triggered once when the view first initializes and renders.

On custom cell actionEvent

Triggered when an interactive element inside a custom cell (Button, Switch, Icon, Link, or HTML template with data-action) is clicked by the user.

actionNameString — Name of action configured in column rule or template data-action attribute.
rowDataObject — Complete data object for the active row.
columnNameString — Original key field name for the column.
cellValueANY — Raw value in this specific cell.
eventObject — DOM click event object.
On ChangeEvent

Triggered whenever pagination internal state changes (navigating pages, changing page size, or refreshing data).

On row selected by userEvent

This event is fired when the user selects a row with a radio button or check box.

rowObject — the selected row data object.
On all rows selectedEvent

This event is called when the user clicks the Select All check box when the Table is in Multiselect mode. Provides a context variable named "all" to indicate whether all or none of the rows are selected.

allBoolean — To indicate whether all or none of the rows are selected.
On forwardEvent

Triggered when the user or script navigates forward to the next page or the last page.

On backwardEvent

Triggered when the user or script navigates backward to the previous page or the first page.

On refreshEvent

Triggered when the user clicks the refresh button or when the refresh() API is called.

On set page sizeEvent

Triggered when the page size is changed via the dropdown or the setPageSize() API.

newSizeInteger — the newly selected page size.
On resetEvent

Triggered when the view is reset, clearing the history and returning to page 0.

On invokedEvent

Triggered immediately before calling the pagination data service. Ideal for starting loading spinners or locking UI elements.

On resultEvent

Triggered when the pagination data service successfully returns a payload.

dataList of Objects — current page array items.
totalCountString — total records from the database.
newCursorString — pagination bookmark token.
columnConfigurationsList of NameValuePairs — the dynamic column configuration.
On sorting by column headerEvent

Triggered when the user clicks the sort icon in a table column header. Notice: The built-in sort action only sorts the specific records currently loaded on the screen (client-side). To perform a true full-database sort, use this event to capture the col and order, update your service inputs, and trigger a fresh fetch.

colString — The key field name or identifier(key) of the column being sorted.
orderString — The new sorting direction applied to the column. Expected values are "ascending", "descending", or "none".
On errorEvent

Triggered if the pagination service fails, times out, or throws an exception.

errorObject / Exception — failure details.

Public methods

Call these from other views or event handlers with ${YourViewId}.methodName();. Extensive pass-through methods exist to control the inner table's state dynamically.

Pagination & Flow Control

execute(customDataInput)Method

Optionally overwrites the input variable, resets pagination to page one, and forces a fresh service call.

refresh()Method

Reloads the current page in place, preserving the current pagination position.

refreshUI(redrawTableCells)Method

Re-renders pagination controls, visibility options and the page-size dropdown without calling the service. Pass false to skip redrawing table cells.

reset(forceRefresh)Method

Clears pagination state back to page one and an empty cursor history. Pass true to also trigger a service call immediately.

getNextData() / getPreviousData() / getFirstData() / getLastData()Method

Programmatic equivalents of the Next, Previous, First and Last buttons. getLastData() only works when totalCount is known.

setPageSize(newSize)Method

Changes the page size, re-anchors the current position to the equivalent absolute record offset when possible, and re-fetches.

getCurrentPageNumber() / getMaxPageIndex()Method

Return the 1-based current page number, and the max page index count (0 when the total record count is unknown).

getPageIndex() / setPageIndex(idx)Method

Get or set the 0-based page index. Setting the index programmatically will trigger a service fetch.

getPageSize()Method

Returns the currently active page size (number of rows in a given page).

Data & Selection Access

getDataList()Method

Returns the array of records currently rendered on the visible page.

clear()Method

Clears all records from the currently rendered table view.

getRecord(idx, asInTable) / getRecords(asInTable)Method

Return the record at a specific 0-based index or the full array of records on the current page. If asInTable is true, it respects any client-side sorting applied to the inner table.

getRecordCount(asInTable)Method

Returns the number of records currently rendered in the table.

getSelectedIndex(asInTable) / getSelectedRecord(asInTable)Method

Return the selected row's index or full record data (for single-selection mode), from the currently rendered page.

getSelectedIndices(asInTable) / getSelectedRecords(asInTable)Method

Return an array of selected indices or record objects (for multi-selection mode).

getSelectedRecordCount(asInTable)Method

Returns the number of records currently selected by the user.

isRecordSelected(record, asInTable)Method

Returns true if a specific record (by index or object reference) is currently selected.

setRecordSelected(record, selected, asInTable) / setAllRecordsSelected(selected, asInTable)Method

Programmatically select or unselect a specific record or all records on the current page.

Styling & View Port

getColumns()Method

Returns the internal column specification objects generated by the dynamic column engine.

setHeadersVisibility(boolList)Method

Sets the visibility of the table headers based on an array of boolean arguments mapping to columns.

getColorStyle() / setColorStyle(style)Method

Gets or sets the table header contextual color theme ("DEFAULT", "PRIMARY", "SUCCESS", etc.).

getTableStyle() / setTableStyle(style)Method

Gets or sets the table CSS style architecture ("DEFAULT", "ELEGANT", "BORDERED", "STRIPED", "HOVER ROW", "CONDENSED").

getHighlightSelection() / setHighlightSelection(highlight)Method

Gets or sets (boolean) whether a row is highlighted visually when selected.

getWidth() / setWidth(width)Method

Gets or sets the outer CSS width of the table control container (e.g., "100%", "800px").

06 — Column Configurations Engine

Turning a text column into a live component

columnConfigurations is a list of name/value pairs returned by the data service. name is the exact property on your data object; value is a stringified JSON object describing how that column should render. You never configure these columns inside the Coach View designer — the view parses this list and renders custom cells automatically.

The interpolation engine — {{ }}

Any string property inside a column's JSON can reference the current row using double curly braces. We explicitly label which properties are parsed by the engine for interpolation below.

// Simple field reference
"{{customerName}}"

// Inline JavaScript expression — ternaries, math, comparisons
"{{ status === 'Active' ? 'Green' : 'Red' }}"
"{{ price * 1.2 }}"

Global properties

These apply to a column's JSON configuration regardless of component type. They establish the container and column layout itself.

PropertyInterpolationDescription
labelNoOverrides the default column header text.
showLabelNoShows or hides the column header text.
widthNoCSS width for the column, e.g. "150px", "20%".
cssNoCustom CSS class(es) applied to the rendered cell.
visibilityNoIf false, the column is hidden entirely from the DOM.
sortableNoIf true, allows the column to be sorted by clicking the header. Note: Default behavior sorts the current page client-side and fires the sort event.
columnOrderNoDetermines left-to-right column order; lower numbers sort first.

07 — Backend Contract

Data service input & output

Any service bound to the Pagination data service must accept these inputs and may return these outputs. The bundled Default Table Paginated Data Service uses exactly this contract.

Input

VariableTypeDescription
dataANYWhat it is: The payload or search criteria sent from the UI to the service. Because it is of type ANY, you can map complex business objects, search filters, or simple strings here.

How to use it: Use this to pass any specific conditions your database query needs (e.g., passing {"status": "Active", "region": "US"} to filter the paginated results).
pageIndexStringWhat it is: The current page number the user is requesting. Important Note: This is 0-indexed. This means Page 1 is sent as "0", Page 2 is sent as "1", and so on. Make sure to convert this to an Integer in your service script to calculate your SQL offset.
pageSizeStringWhat it is: The maximum number of records to return for the current page.

How to use it: Usually defaults to "10", "20", or "50". Multiply this by the pageIndex to calculate exactly where your database query should start fetching records (the offset).
cursorStringWhat it is: A "bookmark" used for cursor-based pagination.

How to use it: If your backend API or database uses cursors instead of standard offsets, this variable will contain the unique string ID of the last record seen. The service should use this token to fetch the very next batch of data. Leave blank if using standard index/size pagination.

Output

VariableTypeDescription
resultANYWhat it is: The actual list of data you are returning to the table to be displayed.

How to use it: Assign your fetched database records to this variable. Even though it is type ANY, you should pass it an array of objects. The View will automatically parse this array and populate the table rows.
totalCountStringWhat it is: The total number of records available in the database across all pages.

How to use it: If you know the exact number of rows (e.g., from a SELECT COUNT(*) query), return it here (e.g., "142"). If calculating the total is too slow or impossible, return "-1" or leave it blank. The UI will gracefully adapt by hiding the "Last" button and calculating pages dynamically.
newCursorStringWhat it is: The new "bookmark" token for the next page of data.

How to use it: If using cursor-based pagination, return the ID or token of the last item in your result array here. The UI will store this and pass it back into the cursor input when the user clicks the "Next" button.
columnConfigurationsNameValuePair[]Optional list of {name, value} pairs. name is the exact property name in your data object; value is a stringified JSON object containing the rendering rules and component properties for that column. (See the Column Configurations Engine section above).

Remember the zero-index: the most common integration bug is treating pageIndex as 1-based. Page 1 in the UI is always requested as pageIndex = "0".
